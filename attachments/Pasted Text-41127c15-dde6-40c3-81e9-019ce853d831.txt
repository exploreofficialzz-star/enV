BUILD enV — GLOBAL ALL-IN-ONE UTILITY PLATFORM

You are a senior full-stack engineer, frontend architect, UI/UX designer, performance engineer, SEO engineer, security engineer, and product architect.

Your task is to build enV, a production-ready global utility platform containing 900+ useful tools, with an architecture that can continuously grow beyond 900 tools.

This is NOT a prototype, demo, mockup, landing page, or proof of concept.

Build the actual application systematically and professionally.

---

1. BRAND

Product name

enV

Use the exact brand name:

enV

Do not rename it.

The platform should feel like a universal digital utility platform where users can find tools for everyday tasks, developers, creators, businesses, students, designers, and technical users.

The platform should be capable of expanding far beyond the initial 900 tools.

Possible positioning:

enV — Useful tools. One place.

Do not make the tagline dominate the interface.

4. MOST IMPORTANT ARCHITECTURE RULE

CLIENT-SIDE FIRST

Every tool must be analyzed before implementation.

Ask:

«"Can this tool perform completely inside the user's browser?"»

If YES:

Implement it client-side.

Do NOT send the user's data to a server unnecessarily.

Examples:

- JSON formatter → browser
- JSON validator → browser
- Base64 encoder/decoder → browser
- URL encoder → browser
- UUID generator → browser
- Password generator → browser
- QR generator → browser
- Image resizing → browser
- Image compression → browser
- Image cropping → browser
- Image conversion → browser where browser APIs/library support it
- Color tools → browser
- Calculators → browser
- Unit converters → browser
- Text tools → browser
- Regex tools → browser
- Markdown tools → browser
- JWT decoder → browser
- Timestamp tools → browser
- CSS generators → browser
- Screenshot/mockup generation → browser where practical
- Random generators → browser
- Many PDF operations → browser where technically practical
- Many audio operations → browser using Web Audio/WebAssembly where practical

The user should not have to upload data to a server when the browser can process it.

---

5. WHEN TO USE BACKEND

Use backend/server infrastructure ONLY when genuinely necessary.

Examples:

- Authentication
- User accounts
- Saved projects
- Cloud storage
- User history that needs persistence
- Synchronization between devices
- AI API calls requiring secret keys
- Server-side processing that cannot reasonably run in browser
- Subscription management
- Premium account management
- Usage limits
- Server-side queues
- Heavy processing that cannot reasonably run client-side
- Admin functionality
- Analytics that genuinely require server-side persistence

Do not create backend APIs simply because an API is possible.

Use Supabase selectively.

Potential Supabase usage:

- Authentication

- Basic conversions

- Browser-side random generators
- Tools that don't require persistent data

Most of enV should work without a user account.
