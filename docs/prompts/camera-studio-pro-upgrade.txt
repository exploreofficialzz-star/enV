enV CAMERA STUDIO — PROFESSIONAL CAMERA UPGRADE PROMPT
Version: 1.1
Purpose: Continue the Camera Studio implementation into a dependable, phone-first camera experience while preserving enV's familiar, ordinary interface.

ROLE
Act as a senior mobile camera engineer, computer-vision engineer, performance engineer and product designer working inside the existing enV repository. Inspect the current implementation and project conventions before changing files. Do not create a separate camera application or replace enV's design system.

PRODUCT GOAL
Build a simple camera that feels familiar to anyone who has used a normal phone camera. Keep the main screen uncluttered: live preview, Photo/Video switch, one capture button, front/rear switch, recent captures and a small set of quick controls. Put advanced settings behind a simple settings area. Professional capability must not make the interface complicated.

CURRENT BASELINE
Camera Studio is integrated across the web app, Android CameraX and iOS AVFoundation. The browser version includes permission-gated preview, front/rear switching, photos, video with microphone fallback, eight color looks, requested 720p/1080p/4K and 24/30/60 fps targets, hardware-reported zoom/exposure/torch, framing grid, timer, a temporary local gallery, download, and recording recovery.

The native applications have separate camera screens. Android includes photo/video capture, contextual permissions, silent-video fallback, front/rear switching, torch, zoom, tap-to-focus, exposure compensation, document-picker export, timer, grid, device-aware quality/frame-rate targets, supported rear-lens selection, manual ISO/shutter, white-balance presets and focus lock. CameraX/Media3 color looks run in preview and capture outputs. Optional ML Kit face tracking draws original glasses, crown and face-following soft-glow overlays into preview and recorded video; face analysis is local, off by default and disabled in photo and dual-camera modes. Camera2 video stabilization is exposed only when the active camera reports support. A dedicated front + rear video mode uses CameraX concurrent-camera composition to record one combined clip on supported Android 11+ devices; each concurrent stream requests hardware stabilization independently when supported. Unsupported phones retain the normal single-camera path. Requested quality and frame rate are not guaranteed on every phone.

iOS includes photo/video capture, session interruption and media-service-reset recovery, all eight Core Image looks in preview and recorded video, timer, framing grid, Photos export/share, recent-capture management, zoom, torch, tap-to-focus, exposure compensation and actual active-format reporting. Manual ISO/shutter, white-balance presets, focus lock and optical-lens selection are shown only when supported by the active camera. Vision face-landmark tracking provides original glasses/crown overlays and subtle face-only softening in preview and recorded video; effects are local, opt-in and video-only. AVFoundation video stabilization uses the active connection's automatic mode only when supported, including separate preview/output support checks in dual-camera mode.

The browser dual-camera path requests a second, distinct camera device only after the user enables it. When the browser and phone permit both streams, the preview and exported photos/videos are composited as picture-in-picture or split view. Each feed is mirrored independently once, including selfie photos and video exports. If the second stream cannot open, the tool reports that condition and retains single-camera use. It never duplicates one stream to simulate two cameras.

Current limits that remain real:
- Adaptive quality fallbacks are source-implemented but not device-accepted: Android tries HD then SD for a reported concurrent pair; iOS tries 720p/30 then low-power 480p/24; browser tries 720p/30, 480p/24 and 240p/15 for the second stream. Actual output settings and encoded playback must be measured on devices.
- Physical-device acceptance has NOT RUN. Android emulator and iOS simulator checks do not prove camera/encoder behaviour on Tecno, Infinix or iPhone hardware. The acceptance matrix remains NOT RUN and the PR must not be release-accepted until real-device evidence is attached.
- Android concurrent front/rear capture uses the Android 11+ public concurrent-camera API and requires a reported front/rear pair. It retries the encoder profile at SD when 720p binding fails. Android 9/10 must not be advertised as supporting simultaneous front/rear through this CameraX path: Android 9 logical multi-camera support does not guarantee concurrent streaming between separate front and rear camera IDs.
- The included glasses, crown, soft-glow and subtle iOS face-softening effects are original enV samples, not a licensed Snapchat Lens catalogue or Snap Camera Kit integration.
- Android Soft glow is a face-following light overlay, not skin smoothing. Full 3D meshes, occlusion-aware masks, expression/blendshape effects and advanced skin retouch are not implemented.
- Face effects are not enabled during simultaneous front/rear recording. They must remain opt-in and off by default.
- Browser camera support depends on secure context, permission, browser APIs and actual device capability. Browser face-tracking AR effects and native-style manual ISO/shutter controls are not implemented.
- Android/iOS manual controls, stabilization and optical lenses are hardware/format-gated. Availability and actual video quality vary by phone and must be measured rather than assumed.
Treat these as real gaps. Never report them as completed.

PHASE 1 — COMPLETE NATIVE CAMERA INTEGRATION
1. Add a dedicated native Camera Studio route on Android and iOS. Use each platform's real camera frameworks rather than embedding the web camera.
2. Android: use AndroidX CameraX (Preview, ImageCapture and VideoCapture/Recorder) with lifecycle-aware binding. Use the existing enV theme and permission patterns.
3. iOS: use AVFoundation (AVCaptureSession, AVCapturePhotoOutput, AVCaptureMovieFileOutput or a supported video-data pipeline). Use the existing SwiftUI navigation, theme and file-saving conventions.
4. Camera and microphone permission requests must be contextual. Explain why microphone permission is requested and allow silent video when microphone access is declined.
5. Implement start/stop preview, photo capture, video recording, camera switching, timer, grid, flash/torch, zoom, focus, exposure and supported quality modes.
6. Add clear camera-busy, permission-denied, no-camera, capture-failed, storage-low and recording-finalization states.
7. Stop sessions and release all camera, microphone, encoder and preview resources when the screen closes or the app enters a lifecycle state that requires release.

PHASE 2 — DEVICE-AWARE PRO CAMERA CONTROLS
1. Offer sensible targets: 720p, 1080p and 4K where supported; 24, 30 and 60 fps where supported. Never show a requested value as if it were the actual output. Read back and display actual device settings.
2. Add focus modes and tap-to-focus only where the device framework supports them.
3. Add exposure compensation, white-balance modes, hardware zoom, flash and video stabilization only when the active device/connection reports support. Android Camera2 and iOS AVFoundation stabilization are implemented with hardware gating; dual-camera feeds request stabilization independently.
4. Add aspect-ratio choices such as 4:3, 16:9 and square. Ensure preview framing matches the exported result.
5. Avoid promising RAW/DNG, HDR, optical zoom, 4K60 or high-frame-rate slow motion until the exact device and encoder path can produce and save those formats.
6. Include a simple reset-to-auto option so users can recover from manual settings.

PHASE 3 — TRUE FRONT + REAR SIMULTANEOUS RECORDING
This is not the same as switching between cameras.
1. Android: implemented using CameraX concurrent mode. The app checks Android 11+ and FEATURE_CAMERA_CONCURRENT, verifies a front/rear concurrent combination, and binds shared Preview and VideoCapture use cases so CameraX records a single composed stream. The dual-camera path uses an HD target to reduce pressure; actual output and availability remain device-dependent. Physical-device tests are still required. The first release uses CameraX's default concurrent composition layout; an interactive PiP/split layout selector is not yet exposed.
2. iOS: implemented with AVCaptureMultiCamSession, isMultiCamSupported, selected multi-camera formats, manually connected preview/data outputs, synchronized front/rear frames, a Core Image PiP composite and AVAssetWriter output. Microphone permission is optional; hardwareCost and systemPressureCost are checked before running. The output targets 720p/30 fps. Physical-device tests for audio sync, orientation, thermals, interruptions and finalization remain required.
3. On devices that do not support simultaneous capture, show a clear unavailable state and retain normal single-camera operation.
4. Test front + rear capture, audio synchronization, orientation, device heat, battery drain, app backgrounding, and recording finalization on real devices.
5. Do not simulate dual camera by showing the same stream twice, and do not imply that a device supports dual capture just because it has two lenses.

PHASE 4 — CREATOR FILTERS AND FACE EFFECTS
IMPLEMENTED ON NATIVE PLATFORMS
1. Keep the eight simple color looks: Natural, Warm, Cool, Mono, Vivid, Fade, Sunset and Glow.
2. Android uses bundled on-device ML Kit face detection/tracking with CameraX timestamp-matched overlay frames. Original glasses, crown and face-following soft-glow effects are drawn into preview and recorded video.
3. iOS uses Vision face landmarks and Core Image/AVAssetWriter. Original glasses and crown overlays plus subtle face-only softening are included in preview and recorded video.
4. Native face effects are opt-in, off by default, local to the device and video-only. They are disabled in Android still-photo and simultaneous front/rear modes; iOS dual-camera mode also does not include face effects.
5. Native color looks and face effects use the same processed frame path for preview and video export. Continue measuring preview-to-export parity on real devices.

NOT YET IMPLEMENTED
1. Browser face-landmark AR effects.
2. Licensed Snapchat Lens catalogue or Snap Camera Kit integration.
3. Expression-driven blendshapes, a full 3D face mesh, occlusion-aware effects and advanced skin retouch.
4. Android skin smoothing. Android Soft glow is a face-following light overlay, not skin retouch. The iOS Beauty sample is subtle face-only softening, not a professional beauty studio.
5. Face effects during simultaneous front/rear recording.
6. A broader catalogue of original masks/effects with tested performance on lower-end phones.

Do not overstate these limits. Keep model assets packaged and licensed, inference off the UI thread, and face frames/landmarks local.

PHASE 5 — STORAGE, EXPORT AND PRIVACY
1. Save captures to the user's device gallery/library with platform-appropriate permissions and clear success/failure confirmation.
2. Keep a recent-captures view with preview, delete, share and save actions.
3. Preserve meaningful filenames, correct MIME types, timestamps, orientation and supported photo metadata.
4. Avoid silently keeping large originals in memory. Stream or write recordings safely and handle storage pressure before recording.
5. Do not upload camera frames, photos, videos, audio or face landmarks to enV servers unless the user explicitly invokes a feature that requires upload and confirms it.
6. Provide clear privacy messaging before camera and microphone access.
7. Add leave-page/app-background handling so in-progress videos are either finalized, explicitly discarded or recovered safely.

DESIGN RULES
- Preserve enV's current typography, spacing, border, surface, radius, theme and button conventions.
- Make the default path feel like a normal phone camera, not a video-editing dashboard.
- Keep the capture button visually central and the most important control.
- Use labels that ordinary users understand: Photo, Video, Switch camera, Timer, Filters, Quality, Flash and Recent captures.
- Avoid decorative panels, excessive cards, oversized headings and unnecessary status badges.
- On narrow screens, keep preview and capture actions prominent; put additional controls below or behind Settings.
- Support light and dark themes, keyboard accessibility on web, screen readers and large text.

TESTING AND RELEASE GATES
1. Run the repository's full type-check, lint, unit tests, catalog checks, build checks and native Android/iOS CI.
2. Add specific Camera Studio regression tests for permissions, switching, photo capture, video recording, filter rendering, quality read-back, lifecycle cleanup, local save and error handling.
3. Test on multiple real Android devices including Android 10/11+ and at least one low-memory phone; do not assume CameraX concurrent-camera support is universal.
4. Test multiple iPhones/iPads with and without multi-camera support.
5. Test front/back switching, denied permissions, missing microphone, low storage, app backgrounding, calls/interruptions, landscape orientation and long recordings.
6. Record measured output resolution, fps, file size, thermal behaviour and battery usage. Avoid marketing claims that have not been measured.
7. Keep feature flags or capability gates for dual-camera and face effects until real-device acceptance passes.
8. Update the native catalogue, billing profile/audit contracts, documentation and tests together whenever the tool's platform scope changes.

DELIVERY EXPECTATION
Work in small, reviewable commits on a feature branch. Do not alter unrelated enV categories or tool behaviour. After each phase, run its checks and inspect the diff. Keep a clear implemented / device-dependent / not-yet-implemented list. Only request or perform the merge once required CI is green and the PR is mergeable. Never mark a native or device-specific feature complete based only on source code compiling.
